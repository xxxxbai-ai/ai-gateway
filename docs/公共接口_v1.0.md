# 公共接口 1.0：我们五个人怎么把程序接起来

先看这份说明。需要修改 C++ 的同学，再查 [代码细则](公共接口_v1.0_代码细则.md)。
“公共接口 1.0”是交接约定的版本；“项目 V0.1”是软件做到哪一步，两者分别计数。

## 1. 我们到底在做什么

用户在聊天窗口输入问题，程序替他选择一个模型，再把回答显示出来。

五个人分工如下：

| 人 | 负责什么 | 一句话理解 |
| --- | --- | --- |
| E | Qt 聊天窗口 | 收到用户的问题，最后显示回答 |
| A（你） | C++ 网关 | 接收问题，依次安排 B/C/D 工作，再把结果交回窗口 |
| B | 问题分类 | 判断是编程、数学、翻译、写作，还是一般问答 |
| C | 模型选择 | 根据题型和模型设置，决定让谁回答 |
| D | 模型调用 | 真正把问题发给选定模型，拿回答或失败原因回来 |

这里的“模块”，就是某个人负责的那一部分程序。

目标流程是：

```text
用户输入 → E 发给 A → A 找 B 判断题型 → A 找 C 选模型
        → A 找 D 取得回答 → A 整理结果 → E 显示
```

这是要完成的流程。当前已有窗口与模拟网关的收发、B 的独立分类；
完整流程仍需大家继续接起来验证。

## 2. “接口”就是交接约定

比如 A 把“计算256的平方根”交给 B。B 按约定交回三项信息：

| 程序里的名字 | 人话是什么意思 | 这个问题的例子 |
| --- | --- | --- |
| `task` | 问题属于哪一类 | `math`，表示数学 |
| `reason` | 为什么这样判断 | 命中了“计算”等规则 |
| `uncertain` | 这次是不是拿不准 | `false`，表示现有规则得出了明确归类 |

`true` 表示“是”，`false` 表示“否”。规则给出明确归类不代表任何问题都绝对判对。
拿不准时，B 返回一般问答，并写明原因。

大家约好名称和含义后，A 就能读取 B 的结果，再交给 C。
**公共接口，就是全组共同使用的这份交接约定。**

这次已经把交接约定写进两个文件：

- `shared/contracts.h`：规定交接单里有哪些信息。
- `shared/module_api.h`：规定可以找 B/C/D 做哪些事、交给他们什么、拿回什么。

`.h` 文件通常写声明，让别人知道怎么调用；`.cpp` 文件写实际做事的代码。
所以有了公共头文件，还需要每个人把实际功能接到它上面。

## 3. 前面那些词，分别是什么意思

| 词 | 在我们项目里是什么意思 |
| --- | --- |
| 函数 | 一段可以被其他代码调用来完成某件事的代码，例如“分析问题” |
| 函数签名 | 调用这段代码要用什么名字、交什么输入、拿什么输出 |
| 字段 | 一项有名字的信息，比如上面的 `task` |
| 数据结构 / `struct` | 把相关的几项信息放在一起；例如把类别、理由、不确定标志合成一份分类结果 |
| 适配、包装 | 保留原来的处理代码，在交接处转换成统一格式 |
| 联调 | 把几个人的程序接起来，实际跑一次完整过程 |
| 配置 | 可以修改的设置表，例如有哪些模型、是否启用、各项能力分是多少 |
| HTTP 请求 | E 和 A 在各自运行的程序之间发送消息的方法 |
| JSON | 发送消息时使用的一种文字格式，用名称和值记录信息 |
| 模拟 / mock | 按预先写好的规则返回测试文字，用来检查程序能否正常连接和处理 |
| 真实模型 | 实际连接外部 AI 服务取得回答 |
| 备用切换 / fallback | 满足约定的失败条件时，由 A 再尝试一个备用模型；本版最多一回 |

例如“适配”可以这样理解：
假如某段原代码输出的是中文“数学”，统一格式要求 `math`，
就在交接处把“数学”转换成 `math`，原来的判断方法可以继续使用。

B/C/D 在同一个 C++ 网关里可以通过函数合作；
E 的窗口和 A 的网关则通过 HTTP 消息合作。
这两种交接方式都要事先约好格式。

## 4. 每个人这轮先做什么

| 人 | 先做的事情 | 交付时给大家看什么 |
| --- | --- | --- |
| A | 维护交接约定，再把 B/C/D 的功能接进网关 | 一个问题按顺序经过各部分的实际结果 |
| B | 分类接口已经补齐，继续维护规则和样例 | 类别、理由、是否拿不准；现有样例的运行结果 |
| C | 先让已有选模代码按统一格式接收、返回信息；后续功能按开发计划补齐 | 输入“数学”等题型，返回模型编号和选择理由 |
| D | 给已有调用代码接上统一入口，继续验证真实模型 | 一个模型的回答或失败原因、调用耗时、运行步骤 |
| E | 使用约定好的消息格式收发，逐步补结果和错误展示 | 在窗口中提问、看到回答及相应信息 |

现有业务代码可以保留，交接处按统一格式转换。
C/D 的部分公共函数目前只有声明，实际实现或转换还要各负责人完成。

每人交付时说清四件事即可：

1. 代码在哪。
2. 怎么运行。
3. 用了什么输入，实际得到了什么结果。
4. 还有什么没完成或卡住。

## 5. GitHub 的几个词怎么理解

| 词 | 意思 |
| --- | --- |
| 仓库 | 全组放代码、说明和修改记录的地方 |
| 提交 / commit | 给一组修改留下一条保存记录 |
| 分支 / branch | 在同一个仓库里单独推进的一条开发路线 |
| `main` | 全组的主要代码分支 |
| 上传 / push | 把本机的提交发送到 GitHub |
| PR / 合并请求 | 展示一组修改，准备把它们加入另一条分支的页面 |
| 合并 / merge | 把这些修改加入目标分支，例如加入 `main` |
| 拉取 / pull | 把 GitHub 上的新提交取回本机；本机有改动时需要妥善保留 |

这次的接口文件和 B 改动放在 [开发分支](https://github.com/xxxxbai-ai/ai-gateway/tree/public-contracts-v1-20261026)。
它目前叫 `public-contracts-v1-20261026`。此前建立的合并请求 #1 已关闭，尚未合入 `main`。

因此，**“已经上传”与“已经进入 main”是两个步骤。**
现在发上面的链接，组员就能查看这份约定；合并后，组员更新 `main` 就能取到这些文件。
合并只更新共享代码，C/D 等部分仍需继续实现和联调。

## 6. 现在验收到了哪一步

- B 的分类函数和公共格式已接好，已有样例检查通过。
- 公共头文件和示例能编译，说明这些声明可以被调用方使用。
- C/D 按新格式提供的实际功能、真实模型回答、完整窗口流程仍需继续验证。

“编译通过”是代码能被构建成程序；
“自己的样例通过”是这部分在那些样例上表现正确；
“整体完成”还要实际跑通全组流程，并满足对应版本的验收要求。

你现在先读懂第 1、2、4、5 节，知道谁交给谁什么。
需要编写具体代码时，再查 [字段、函数和错误处理细则](公共接口_v1.0_代码细则.md)。
